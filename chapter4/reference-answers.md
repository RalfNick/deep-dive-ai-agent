# 第 4 章练习参考答案

这些答案用于核对关键边界，不要求与示例措辞完全一致。架构题只给出一种可辩护方案；如果你的方案明确了责任、失败状态、证据和限制，同样可以成立。

## 基础题

### 基础题 1：为什么相同模型会表现得像不同 Agent

模型只产生下一步候选。产品还会决定它看见哪些上下文、能调用哪些工具、哪些动作需要审批、命令在哪里执行、状态是否持久化、何时停止以及什么证据算完成。模型权重相同而这些边界不同，系统层面可观察到的成功率、安全性和恢复能力就会不同。

### 基础题 2：能闭环的 Loop 为什么不等于可靠 Harness

闭环只说明系统能反复执行“决策—行动—观察”。如果上下文、权限、执行、状态、验证和日志全部内联在一个 `while` 中，它们难以单独替换、测试和审计；进程退出后也可能只剩聊天历史，无法知道副作用是否已经发生。Harness 的关键是明确拥有控制流，并把这些责任拆成稳定接口。

### 基础题 3：四种标识和制品怎样分工

`call_id` 关联某次模型工具提议与相应结果；一次重试或重新提议通常产生新的 `call_id`。`action_id` 标识 Harness 眼中业务意义相同的动作，例如“为订单 102 创建退款”，需要跨调用和恢复保持稳定。业务幂等键由真正拥有副作用的服务执行唯一约束；它可以直接采用 `action_id`，也可以由“租户 + 订单 + 操作类型”等字段派生。执行回执不是另一个 ID，而是保存动作是否提交、返回结果和状态摘要的持久制品。

最自然的“可以相同”是 `action_id` 与业务幂等键，前提是两边对动作身份的定义完全一致。`call_id` 与 `action_id` 即使在一次性只读调用中偶然同值，也不应被设计成同一概念：前者标识协议调用，后者标识可跨重试的业务动作。

### 基础题 4：权限策略与沙箱为什么要同时存在

策略层根据工具、参数、身份和风险做 `allow/deny/ask` 判断，属于“应该不应该做”。系统级 Sandbox 依靠文件、进程和网络隔离限制真实能力，属于“实际上能不能做”。本章的 `WorkspacePathGuard` 只负责应用层路径包含关系，不能替代 OS 隔离。策略可能漏判或被提示注入影响；Sandbox 也可能配置过宽。两层独立存在才形成纵深防御。

### 基础题 5：模型最终文本为什么不能直接代表完成

`protocol final` 只表示模型结束当前协议。例如模型说“已修复”，但测试仍失败，此时协议结束而 `task accepted=false`。`task accepted` 表示机器验收合同通过，例如测试和静态检查均通过；但如果需求其实是“货币符号应保留在界面”，实现却删除符号，用户仍可拒绝，即 `user accepted=false`。反过来，在一次探索性脚本中，用户可能人工确认输出已经满足临时目标，即 `user accepted=true`，但团队尚未建立自动测试，所以不能伪造 `task accepted=true`。三层应分别记录，而不是让最终文本替代证据。

## 实验题

### 实验题 6：让敏感路径进入 `ask` 而不是 `deny`

修改 `chapter4/harness/gateway.py`，把敏感路径处理改为返回 `GatewayDecisionKind.ASK`，然后更新 `chapter4/tests/test_gateway_path_guard.py`。预期变化是策略决定从 `deny` 变为 `ask`，但 `../secret.txt` 仍应被 `WorkspacePathGuard` 阻止。这个实验只证明应用层路径守卫没有随审批策略一起放宽；它没有证明子进程、网络或凭据已被 OS Sandbox 隔离。

### 实验题 7：把最大重试次数改为 0

在 `run_fault_case()` 创建 `HarnessRuntime` 时传入 `max_retries=0`。`transient_once` 与 `timeout_once` 的 `attempts` 会从 2 变为 1，状态从 `waiting_approval` 变为 `failed`。永久错误不受影响，因为它本来就不可重试。

### 实验题 8：破坏检查点与审批事件顺序

在 `chapter4/harness/runtime.py` 中把 `approval_requested` 移到 `checkpoint_saved` 之前，并运行 `grade_trace()`。预期 `missing_contracts` 包含 `checkpoint_before_approval`。完成实验后应恢复正确顺序，不能把错误实现留在主线代码中。

### 实验题 9：移除 Verifier

运行 `inline_loop_demo.py` 或查看边界矩阵的 `verifier_missing` 案例。预期 `accepted=false`、`false_completed=true`、`sample_count=1`。Trace 合同仍可能通过，因为它只检查事件的顺序和因果关系；系统完全可以忠实记录一次错误完成。这不是说所有无 Verifier 系统必然失败，而是说明该固定案例的最终文本没有外部验收依据。

### 实验题 10：制造副作用未知结果

在 `RepairEnvironment.execute()` 中增加一个故障：先写入文件，再返回 `timeout`。如果 Runtime 在没有回执查询的情况下直接重试，副作用计数可能大于 1。正确改进不是简单增加重试次数，而是让工具系统以稳定 `action_id` 查询或返回已提交结果。

建议路径是：超时后先进入 `UNKNOWN_RESULT`；查询本地 Receipt，再用同一业务幂等键查询真正的执行系统。若系统返回已提交，复用原结果；若明确未提交且服务端保证同键幂等，才可用原键重试；若仍无法判断，则保持未知并交给人工，不能生成新键重做。

## 设计与批判题

### 设计与批判题 11：审批前最少要保存什么

一个生产数据库迁移审批至少应包含：

- 动作：迁移名称、目标数据库/Schema、执行主体和稳定 `action_id`；
- 参数：迁移脚本摘要、影响表、预计行数、锁策略、超时和分批大小；
- 状态版本：当前 Schema 版本、迁移文件哈希、部署版本和只读预检结果；
- 风险：预计锁时长、容量变化、不可逆字段删除、依赖服务和业务窗口；
- 回滚：反向迁移或备份恢复步骤、触发阈值、负责人及验证命令；
- 过期条件：超过时间窗口、Schema/脚本哈希变化、预检结果变化或审批人权限失效即重新审批。

Harness 还要保存 `run_id`、下一决策位置、待执行调用和此前事件。只保存原 Prompt 不够，因为恢复者不知道批准绑定的是哪个版本，也不知道动作是否已经提交。

### 设计与批判题 12：怎样处理支付工具超时

支付是高风险副作用。可以使用“商户 + 订单 + 支付意图”派生的稳定幂等键。调用超时后进入 `UNKNOWN_RESULT`，按同一键查询支付系统：已成功则复用交易号；明确失败且未扣款才结束；明确不存在且服务端保证同键幂等时才安全重试；持续未知则转人工。不能把网络超时解释为“没有扣款”，模型也不能自行生成新键绕过查询。

最大等待时间必须写入业务合同，而不是藏在 Prompt 里。例如前 30 秒退避查询，随后转异步 `PENDING_RECONCILIATION`；15 分钟仍未知则停止自动动作、告警并交给人工。具体阈值由支付渠道 SLA 和业务风险决定，但超过阈值后的终态与责任人必须明确。

### 设计与批判题 13：上下文压缩前要保存哪些事实

保存任务目标与完成条件、当前计划位置、未决问题、已完成动作及回执、待审批动作、环境版本、最近失败及重试预算、关键文件引用。摘要可以丢弃逐字对话，但不能丢失恢复运行所需的控制状态。压缩策略本身留到第 6 章讨论。

### 设计与批判题 14：怎样判断 Trace 可以安全回放

先区分“重放事件以重建状态”和“重新执行动作”：

| 工具 | 可重放状态 | 可重新执行动作 | 依据 |
| --- | --- | --- | --- |
| 文件读取 | 可以 | 通常可以，但结果可能因文件版本变化而不同 | 只读；应记录路径与版本摘要 |
| 发邮件 | 可以 | 默认不可以；需稳定消息幂等键或查询发送回执 | 重复发送是外部可见副作用 |
| 数据库更新 | 可以 | 仅在事务未提交可确认，或由唯一约束/条件更新保证幂等时可以 | 超时后可能处于未知提交状态 |
| 支付 | 可以 | 不应盲目重试；先按业务幂等键查询支付状态 | 不可逆、高风险且可能重复扣款 |

所以 Trace 中存在调用记录只能用于状态重建，不能自动授权副作用重执行。

### 设计与批判题 15：为什么最强模型仍需要 Harness

“模型更强”主要提高候选决策质量，不会消除系统边界：

1. **概率决策**：同一输入仍可能得到不同计划；预算、停止条件和回归评估不能交给一次采样碰运气。
2. **提示注入**：网页、仓库文件和工具输出可能携带不可信指令；模型能力越强，不代表信任边界自动正确。
3. **不可逆副作用**：发信、付款、删除和生产迁移需要授权、幂等键、隔离和回执，模型无法靠语言保证 exactly-once。
4. **恢复**：进程退出、审批等待和未知结果要求检查点、状态机与结果查询；模型对话记忆不是持久事务状态。
5. **业务验收**：测试通过、合规约束和用户接受来自外部合同；最强模型的“已完成”仍只是候选声明。

因此最强模型可以减少错误决策，却不能替代权限、执行、状态、验证和证据。另一方面，任务若只是一次确定性函数调用，或成熟 Runtime 已覆盖这些责任，也不应为了“工程化”而自建复杂 Harness。

## 扩展实验

### 扩展实验 A：实现 `UNKNOWN_RESULT`

为 `RunStatus` 增加 `UNKNOWN_RESULT`，在写操作“已提交但响应丢失”时进入该状态。新增测试要求：恢复后先查询 `ActionReceiptStore`，存在回执则继续，不存在回执则保持未知并请求人工处理；不得自动重复写入。

### 扩展实验 B：扩大状态版本的覆盖范围

主线代码已经在审批请求中记录 Python 文件摘要，并在恢复时拒绝过期批准。继续把 `state_digest` 扩展为 Git 树、依赖锁文件、数据库 Schema 版本和关键外部资源版本的组合摘要。测试应分别修改未跟踪配置、依赖锁文件和外部版本夹具，确认任何被审批合同声明为关键的输入发生变化时都会进入 `approval_stale`，而无关文件变化不会制造无意义重批。

### 扩展实验 C：把文件 Store 替换为 SQLite

用标准库 `sqlite3` 实现检查点与回执，使用唯一约束保护 `action_id`，在同一事务中写入回执与状态转移。并发启动两个恢复者，断言只有一个能够插入副作用回执。这个实验仍不等价于外部业务系统的分布式事务，但能暴露文件账本没有锁的限制。
