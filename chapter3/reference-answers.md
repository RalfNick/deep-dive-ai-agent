# 第 3 章练习参考答案与验收标准

以下答案给出判断框架，不是唯一措辞。实验题必须附命令、关键 Trace、失败样本和结论边界。

## 基础题

1. **概念边界**：一次生成没有后续路径；增强型 LLM 获得检索或工具能力但可只运行一轮；Workflow 由代码选择预定义路径；Agent 由模型根据新观察动态选择下一步。判断点不是调用次数，而是反馈后路径选择权。
2. **工具边界**：`function_call` 是提议。执行前至少检查 JSON/Schema、业务语义、路径或资源范围、用户权限、审批、预算、幂等和超时。只有运行时返回结果后才能说“已尝试执行”；仍需看 `ok` 才能说成功。
3. **状态边界**：轨迹记录“模型看过失败测试”；环境状态是 `pricing.py` 的实际内容；控制状态是步数、预算和待审批动作。漂移例：轨迹说写入成功但磁盘失败；文件已发出副作用但控制器准备重试；压缩丢掉约束但权限系统仍应生效。
4. **ReAct**：`reason to act` 用目标和证据选择行动；`act to reason` 用行动返回的事实更新判断。工程审计需要输入、动作、结果和验收因果链，不必暴露完整内部推理 Token。
5. **完成协议**：protocol final 只表示本轮无工具调用或输出类型满足；task accepted 表示机器验收合同通过；user accepted 包含用户意图和主观判断。例如模型停止但测试失败；测试通过但用户不接受 UI；用户满意草稿但合规流程尚未通过。
6. **标识符**：`call_id` 关联一次模型提议和结果；幂等键让多次业务请求只产生一次副作用。重试可以有新的传输调用标识但必须复用同一业务幂等键。

## 实验题

7. **新增工具**：验收包括合法 `list_files({})` 成功、未知参数返回 `invalid_arguments`、结果保留原 `call_id`、`../` 越界测试仍通过。不得让工具直接返回临时目录之外的文件。
8. **Patch 冲突**：首个结果应为 `error_type=patch_conflict`、`retryable=False`。后续轨迹必须出现新的 `read_file`，补丁参数应基于新观察变化；相同签名重试判不合格。
9. **进展检测**：状态摘要不变可能是正常读取、测试或轮询，所以还需结合工具语义、是否得到新信息、错误是否变化与时间。建议“环境不变 + 相同决策签名 + 无新证据”联合触发。
10. **超时与取消**：工具超时是运行时限额触发，应包含 `error_type=tool_timeout`；用户取消来自外部控制信号，RunResult 应为 `cancelled`。两者都要记录可能已经发生的副作用。
11. **幂等反例**：无账本时，第一次服务端落账但客户端收到超时，第二次再落一笔；恢复后，同一键返回首次收据且账本条目数为 1。测试必须断言金额与条目数，不能只断言返回 `ok`。
12. **验收合同**：在运行前保存测试文件摘要；验收时同时要求测试退出码 0、`pricing.py` 变化、`test_pricing.py` 摘要不变。违规时 Trace 应明确 `forbidden_change:test_pricing.py`。
13. **Trace 审计**：删除调用事件后，对应结果的 `call_id` 不在调用集合，回放器应在执行任何副作用前失败并报告孤儿 ID。

## 设计与批判题

14. **退款 Agent**：至少包括订单查询、退款资格、退款执行和状态查询工具；金额阈值、身份、订单归属由策略代码校验；退款工具使用业务幂等键；高额、信息冲突或未知状态进入人工；成功要求退款状态、金额与审计记录一致。

    | 停止原因 | 触发者与事实确定性 | 是否直接重试 | 恢复方式 |
    | --- | --- | --- | --- |
    | `tool_timeout` | 工具超过运行时限；副作用是否发生可能未知 | 只在可重试且幂等时重试 | 先用订单 ID / 幂等键查询退款状态，再决定重试或转人工 |
    | `cancelled` | 用户或上层控制面取消；取消前副作用仍可能已发生 | 不自动重试 | 记录取消时刻、已执行动作与补偿状态；由新请求显式恢复 |
    | `budget_exhausted` | 步数、时间、Token 或费用达到硬上限；不是工具失败 | 不原样继续 | 保存检查点、剩余事项和最近证据，重新授权预算后从状态恢复 |

    三种状态不能共用一个“失败”字符串：timeout 影响一次工具调用，cancelled 表达外部意图，budget exhaustion 表达整个 Run 的控制预算。
15. **系统选择**：发票抽取通常是结构化输出 + Workflow；竞品研究路径开放，适合 Agent 加引用验收；生产数据库迁移应以固定变更/审批/回滚 Workflow 为主，Agent 只做分析和草案。若选择不同，必须用风险与路径不确定性证明。
16. **失败分类**：观察错是输入证据错误或缺失；决策错是在正确观察上选错动作；执行错是工具实现或基础设施失败；恢复错是错误后策略不当；停止错是早停或不停；目标错是起始意图/范围错误。主因取最早的必要故障点，多标签记录下游影响。

    最小 20 条轨迹可按下表分配，避免只收集容易成功的修复：

    | 轨迹编号 | 数量 | 场景 | 主要预期标签 |
    | --- | ---: | --- | --- |
    | T01-T08 | 8 | 单一、明确、可验证的普通修复；其中 2 条正常工具瞬时失败 | 成功；瞬时失败样本可附执行错但应恢复 |
    | T09-T12 | 4 | 需求含糊、目标文件冲突、验收口径缺失、用户授权不足 | 目标错或观察错；系统应 `needs_input` |
    | T13-T16 | 4 | timeout、permission denied、patch conflict、结果丢失 | 执行错；若重试不当再加恢复错 |
    | T17-T20 | 4 | 修改测试伪造成功、重复 call ID、无验证 final、步数耗尽仍报完成 | 停止错；可附恢复错或决策错 |

    每条至少记录 `accepted`、`false_completion`、`recovered` 三个布尔标签和一个主因。`accepted` 只能来自外部验收；`false_completion=True` 表示 Run 报 completed 但验收失败；`recovered=True` 表示发生错误后最终仍通过验收。汇总时分别计算：

    \[
    \text{acceptance rate}=\frac{\# accepted}{20},\qquad
    \text{false completion rate}=\frac{\# false\_completion}{\# reported\_completed}
    \]

    \[
    \text{recovery rate}=\frac{\# recovered}{\# traces\ with\ recoverable\ error}
    \]

    分母为 0 时报告“不适用”，不能填 100%。最终提交物应包含 20 行标注表、至少 3 条完整 Trace、主因规则和一处有争议样本的解释。

17. **框架对照**：题目最低要求是三选一。以 LangGraph 为例，可做如下映射：

    | 本章责任 | LangGraph 最小映射 | 仍需应用定义的内容 |
    | --- | --- | --- |
    | `ToolCall` | model node 输出的 AIMessage tool call；条件边路由到 tool node | 调用参数的业务策略与审批 |
    | `ToolResult` | tool node 产生 ToolMessage，并保留对应 tool call ID | 错误分类、脱敏和幂等回执 |
    | 状态 | TypedDict / Pydantic state；checkpointer 按 `thread_id` 持久化 | 哪些字段是权威事实、保留多久 |
    | 停止 | 条件边进入 `END`；recursion limit 是最后保险丝 | completed / failed / cancelled / budget_exhausted 的业务语义 |
    | Verifier | 独立 verifier node；拒绝时回到修复节点，接受后进入交付节点 | 验收规则、受保护文件与状态摘要 |
    | Trace | node、edge、tool call、result 与 verifier 事件 | 敏感字段、审计留存和业务动作 ID |

    最低合格实现必须展示一次工具失败后的条件路由和一次 Verifier 拒绝。框架仍未替你解决的三件事是：业务权限边界、跨重试幂等语义、什么证据才算任务真实完成。
18. **反驳题**：模型输出仍为概率分布；生产环境会遇到训练外状态；外部文本可注入恶意指令；不可逆副作用不能靠事后道歉恢复。更强模型可降低错误率，却不能把访问控制和验收概率化。
