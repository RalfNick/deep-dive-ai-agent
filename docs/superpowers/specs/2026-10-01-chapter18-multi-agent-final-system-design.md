## 1. 目的、读者与成功标准

标题：**第 18 章 Multi-Agent 与最终系统：不是 Agent 越多越好**。总目录的“Multi-Agent 与最终系统”职责不变，不因候选标题而修改公开站点清单。

读者已经了解基本 Agent Loop、上下文、RAG、工具、权限、评估和 Trace，但可能把多 Agent 理解成“多写几个角色提示词，再让它们讨论”。本章回答：**什么时候值得拆分任务，交出去的是什么，返回的结论怎样核实，整个系统由谁负责完成？**

读完后应能：

1. 区分单 Agent 加工具/Skill、固定 Workflow、具有独立决策上下文的多 Agent；不以角色数、模型型号或函数数定义智能体数量。
2. 从任务依赖、上下文范围、工具权限、可验证性和协调成本判断是否拆分，而不是默认“复杂任务必须多人”。
3. 写清任务目标、输入、允许访问范围、预算、输出及验收条件；区分子任务返回与对话控制权交接。
4. 处理重复研究、丢失约束、同源意见、证据矛盾、旧补丁和并行修改冲突；知道多数投票不等于事实验证。
5. 在无需 API Key 的教学包中观察子任务、结果、共享状态、全局预算、取消和最终验收；不把脚本决策的成功称为模型能力。
6. 看懂一个支持知识问答与受控代码修复的最小收官系统，说明哪些机制已运行、哪些只是生产设计要求，并能制定后续 AI 学习、研究和工作实践路线。

正文目标为约 2.2–2.8 万叙述汉字，28–36 个二/三级标题、7 幅原创技术图、4–5 张比较表、5 组实验、至少 4 类可观察失败、13 道分层练习。沿用既有统计口径，叙述汉字与含代码/Markdown 的总字符数分别记录，不用重复免责声明凑字数。

## 2. 已确认方案与范围裁决

采用“协作原理＋小实验＋最终系统”，不写框架 API 百科，也不从零搭建一个庞大的企业平台。三种场景服务不同概念，不强求连续：

- **并行知识调查。** 围绕虚构“星舟工作台”的产品与问答文档，将两个可独立调查的问题交给不同执行者，返回带来源、版本、范围的结论。引入重复调查、相同来源的多票与有效资料之间的矛盾。
- **并行修改冲突。** 两个执行者基于同一旧文件提出补丁；主控怎样发现版本已变、保留先前变化并决定重读。再对比不同文件的独立提议，说明独立工作区仍不能代替合并后的集成验收。
- **收官系统。** 同一入口分别支持“查证后回答”和“提出修改、审批后执行、测试后报告”。它汇合前面各章的责任边界，不强迫每次问答都启动代码修复，也不让一个 Agent 同时拥有所有权限。

最终系统交付的是**可运行的最小知识路径与代码路径，以及共同的协作和验收合同**，不是企业产品。知识路径使用自包含的小型显式事实索引与治理检查，不冒称真实 Embedding/Reranker；代码路径实际修改可信教学工作区中的小型链接检查器并运行冻结的测试与行为验收，不只返回预写的“修复成功”。它映射前章合同，但不动态导入旧章节内部模块，不要求读者同时安装前面所有框架。

第 4/6/9/10 章已有权限、状态、异步和幂等机制；这里只讲其跨执行者的责任变化。第 13/14 章已有评分统计和诊断；这里只增加任务分解、交接、重复工作和团队级不变量。第 17 章已有多模态观察合同；本章解释这些来源、时间与权限如何跨交接保留，不重做真实视觉/语音。部署、安全、成本复盘是收官必需内容，但以架构、验收清单和取舍为主，**不进行实际 Docker、云部署、真实设备或 Provider 验证**。

## 3. 正文四幕与阅读顺序

### 第一幕：为什么两个 Agent 可能不如一个

先给“两个调查者都说对，但引用的是同一份旧资料”的具体问题。随后解释单 Agent、Workflow、多 Agent 的边界：角色是一种任务配置，独立上下文和运行责任才是拆分的重要条件；相同模型可以承载多个执行者，多个模型也可以只服务一个 Agent。

建立任务依赖图，区分可独立调查与必须等待前一步结果的工作。用可手算的协调成本例子说明：若三个独立子任务在教学时钟中各需 7、11、5 单位，串行工作量为 23；理想并行关键路径为 11，加委派 2、汇总 3 后为 16。这只是固定假设的排程计算，不是实测秒数、费用或模型提速比例。任务不能拆分或汇总成本提高时，结论可以反转。

第一组实验保留单执行者对照，固定目标、资料、验收和脚本策略。读者看的是结构与协调代价，不是哪个模型更聪明。

### 第二幕：怎样把任务交出去，而不把责任丢掉

从两段普通中文委派说明开始：含糊的“研究一下”与有边界的具体任务。再逐步引出任务包、上下文最小化、允许工具、证据回传和验收。完整 Schema 留在配套材料，正文先展示能读懂的小样例。

明确两种控制流：**委派**是专家处理子任务后返回，主控继续整合；**Handoff**是当前对话的处理者切换，专家负责后续回应。实现都必须经过共同权限与预算网关；切换角色不会换掉用户身份、提升权限或让原授权自动失效。任务分工不等同于安全沙箱。

解释共享的是哪些状态：用户目标与政策由主控维护，子任务获得必要快照，结果以不可变记录返回。共享全量聊天历史不是默认值，受限信息不能因为被另一个 Agent 摘要过就进入较低权限输出。

### 第三幕：合作为什么会失败

依次观察重复研究、遗漏必要输入、证据矛盾和文件版本冲突。主控不能凭语气自信或多数意见覆盖来源；多票引用同一份材料只增加意见，不增加独立证据。有效材料矛盾且没有明确裁决规则时保留 `conflict`，请求澄清，不悄悄拼接成一个答案。

并行代码提议分别保存在执行者的独立快照中，只有统一提交入口能修改集成工作区。每份提议绑定基线摘要；集成前核对当前文件，过期则拒绝并重读。不同文件无文本冲突，也仍需整体测试。审稿者的“看着没问题”不能替代验收，增加一个 Reviewer 角色也不意味着错误统计独立。

介绍跨执行者全局预算、部分失败、有限重试、取消与停止。取消请求、确认、晚到结果与已发生副作用分开；正常结果到得晚不能把已停止运行重新标为完成。分解与 Handoff 都有深度/次数上限，禁止 A→B→A 无限交接。

### 第四幕：从协作实验到最终系统

逐步组成最小入口、路由、知识调查、代码提议、权限/审批、统一执行、独立验收、状态和 Trace。先跑通一次知识回答，再跑一次真实教学补丁与测试，最后注入无权限知识、缺批准和错误验收。两条路径共用合同，不被强行串联。

把本地责任映射到 LangChain/LangGraph、OpenAI Agents SDK、Claude Code 与 Codex；CrewAI 等只作适用范围旁注，不再另写一套运行实现。产品按 Model、Context、Tools、Runtime、Safety、Evaluation 六维归属解释，不排名、不列易过期功能百科。

最后给“从离线教学到生产”的检查清单：身份与租户、数据治理、动作隔离、持久状态、工作区、队列、观测、评估、预算、版本、灰度和回滚。区分逻辑上下文隔离、独立文件目录、操作系统沙箱三层；本轮只验证前两层的有限教学合同，不把它们写成已具备生产防护。结尾回顾全书学习地图，提供继续做研究、构建应用和参与实际工作的方向，不虚构下一章。

## 4. 实验包与核心合同

新增自包含 `chapter18/`。运行时以 Python 标准库为主，测试和预览复用现存、明确记录版本的环境。核心为 `DecisionPolicy` 可替换接口和固定的 `ScriptedPolicy`：每个执行者拥有独立任务包、观察历史、允许工具、计数和结束状态，依次做出工具提议或结果提议。必须明确这是测试替身驱动的协作 Harness，不把普通函数换个名称说成自主 LLM。

本轮不实现 Live Provider，不读取环境中的 API Key。未来接入真实模型的位置可以说明，但不得提供会默认联网的入口或把真模型运行加入当前验收。

| 合同 | 必需语义 |
| --- | --- |
| `TaskPacket` | 任务/父任务/执行者 ID、目标、已授权用户身份、目标版本、必要输入引用、允许来源/工具/写入范围、输出要求、基线摘要、预算与深度 |
| `WorkerResult` | 所属任务与尝试 ID、结束状态、结论/未完成项、原始来源引用、候选补丁或结果引用、实际使用计数；必须与被委派任务匹配 |
| `EvidenceRef` | 来源 ID、相对位置、实际内容摘要、版本与资格、支持引句；摘要与引句核对只证明字节对应，不自动证明语义蕴含 |
| `RunState` | 当前控制者、任务图、不可变结果记录、当前共享版本、全局计数、挂起审批、取消/停止原因与完成证据 |
| `ActionReceipt` | 提议与执行 ID、授权范围、执行前后摘要、实际执行与验收状态；执行或测试调用不直接等于最终通过 |
| `TeamReport` | Schema、固定案例、输入证据、轨迹关联、状态、派生指标、失败清单和结论限制 |

稳定报告使用 `chapter18.team.v1`。最终状态区分 `answer`、`verified`、`unknown`、`blocked`、`conflict`、`needs_approval`、`stopped`；子任务的 `done` 不等于整体验收通过。停止细分原因放 `reason_code`，避免正文堆状态名称。

默认教学上限：同时在途子任务不超过 3，委派深度不超过 2，Handoff 次数不超过 4，每子任务决策不超过 4 步，暂时性错误最多额外重试 1 次。全局最多 16 次工具调用，其中 2 次保留给最终验证；子任务与重试共同消费剩余预算，不能各自重新领取 16 次。保留额度不是额外额度，最终报告同时给预算、实际使用与未使用量。具体场景可显式收紧额度。

并发实验使用受控逻辑时钟和可重复的完成顺序，既验证不同返回顺序下的合并结果，又保持规范报告确定性。不在规范报告中放真实耗时；实际时钟只能作为另行标注的诊断数据。轨迹通过父任务、提议、调用和尝试 ID 表达因果，不把人为排序伪称真实到达时刻。

知识材料包含可独立调查的问题、旧版本、不同访问资格和两个仍有效但互相矛盾的声明。精确片段输入的规范编码摘要与原文件字节摘要分别记录，派生任务包不能借用未经发送的整份原始文件摘要。返回前重新核对来源资格和目标版本；禁止受限原文/引句泄露到低权限报告。

代码工作区只从仓库内可信教学夹具创建。执行者提出补丁，统一入口检查相对路径、授权、基线与预期差异，实际修改候选源码并运行冻结测试和行为验收。受保护测试、验收资产与笔记不得修改；沙箱、任意代码执行防护和恶意并发目录替换不在本轮证明范围。独立工作区和可信测试进程不能称为生产沙箱。

## 5. 五组实验与可观察失败

每组四个固定案例，共 20 个；案例结果由运行后证据计算，不预设成功率。

| 实验 | 案例与要观察的问题 |
| --- | --- |
| 18-1：一个还是多个 | `single-sufficient`、`parallel-separated`、`serial-dependency`、`duplicate-research`；同一固定任务的覆盖、重复工作、协调调用与逻辑关键路径；简单/依赖任务不硬拆 |
| 18-2：委派与交接 | `delegation-return`、`handoff-transfer`、`context-not-forwarded`、`scope-escalation`；谁继续回应、谁持有目标、缺约束时是否保留未知、是否拒绝权限扩大 |
| 18-3：意见与修改冲突 | `source-version-conflict`、`same-source-three-votes`、`stale-patch`、`disjoint-patches`；两份合格材料矛盾时保留冲突，同源多票不新增依据，旧补丁不覆盖当前修改，不同文件合并仍需验收 |
| 18-4：预算与停止 | `one-worker-timeout`、`global-budget-exhausted`、`cancel-late-result`、`handoff-cycle`；部分失败怎样暴露、验证额度是否保留、晚到结果能否复活停止状态、循环交接能否被阻断 |
| 18-5：收官两条业务路径 | `kb-verified-answer`、`kb-permission-denied`、`repair-verified`、`repair-needs-approval`；带引用知识回答、受限材料拒绝、真实教学补丁/测试/验收、无批准不得执行 |

至少额外用单元故障注入覆盖：暂时错误重试消耗同一全局额度；受保护测试修改；匹配到错误任务的结果；引用不存在或内容已变；重复调用不能重复提交；取消发生在真实教学写入以后不能抹去回执。控制组中不安全的共享状态/覆盖做法只在受控内存模型中展示，不为制造反例绕过真实文件路径与权限网关。

指标为可验证的任务覆盖、重复调查、去重后的有效来源数、未解决矛盾、权限拒绝、过期补丁拒绝、重复提交、实际决策/工具数、预算余量和验收证据。来源去重不能证明统计独立，多个不同文档也可能转述同一原始事实。安全不变量按案例/回执派生，不能写死为零。单 Agent 与团队固定对照只支持机制与排程判断，不证明模型能力、真实延迟或经济收益；没有 Provider Usage 不填 Token 与费用。

输出规范包九文件：五份 `group-N.json`、`team-report.json`、`summary.md`、`exercise-results.json`、`manifest.json`。输出目录必须是新的仓库内 `chapter18/.runs/` 或 `chapter18/reports/` 子目录，禁止静默覆盖。两次完整运行必须逐文件字节一致；错误发生时不能生成看似完整的合格报告。

## 6. 原创图、练习与版式

七幅图延续浅色纸张、手绘描边、蓝绿紫橙分区；中文、数字和箭头用可控矢量排版，保存可编辑源与生成记录：

1. 单 Agent、Workflow、多 Agent：决策上下文与责任在哪。
2. 任务依赖与协调成本：能拆与不能拆的两条路径。
3. 委派返回与 Handoff：谁保留控制、谁接管对话。
4. 任务包与上下文隔离：共享目标，不共享所有内容与权限。
5. 证据/补丁汇合：同源意见、事实矛盾、基线变化与独立验收。
6. 团队生命周期：全局预算、部分失败、取消及晚到结果。
7. 收官系统全景：知识与代码两路，共同连接权限、状态、Trace、评估和改进。

最终图片在 `book/images/chapter18/`，设计源在 `infographic/chapter18/`。正文解释每幅图的读图顺序；不照搬厂商图，不生成难以核实的大量图内小字。表格优先用于概念边界、委派/交接、故障处理、产品责任映射和生产验收。

13 道练习覆盖：边界辨析、任务可拆分性、23/16 单位的手算、任务说明修改、上下文缺失、同源意见、矛盾资料、旧补丁、全局额度、取消晚到结果、知识权限、最终验收及生产取舍。计算题给数值与过程；代码题有运行入口、关键输出和判据；设计题不按术语数打分。完整输入 Schema、长日志与原始证据放配套材料，不让正文退回晦涩的接口说明。
