# 《深入浅出 AI Agent》章节写作标准

本标准用于保证后续章节达到“书稿”而不是“教程提纲”的完整度。它参考了 bojieli/ai-agent-book 的章节密度，但所有文字、案例、图表与实验均围绕本项目重新设计。

## 一章应回答到什么程度

读者读完一章后，至少应该能够：

1. 用自己的话解释概念，并指出它与相邻概念的边界；
2. 顺着数据流或执行流讲清机制，而不是只记住组件名称；
3. 运行一个最小实现，观察中间状态和失败现象；
4. 知道成熟框架、产品或协议如何实现同一机制；
5. 说出适用条件、成本、限制、安全风险与替代方案；
6. 把本章结论连接到全书的最终 Agent 项目。

## 核心章节最低密度

| 项目 | 目标范围 | 说明 |
| --- | --- | --- |
| 正文字数 | 约 1.8 万至 3 万中文字符 | 以讲清问题为准，不用重复表达凑字数 |
| 二至四级标题 | 20 至 40 个 | 每节只承担一个清晰问题 |
| 原创技术图 | 5 至 8 张 | 至少包括概念边界、架构、执行流程 |
| 比较表或清单 | 3 至 6 个 | 用于容易混淆的概念和工程选择 |
| 可运行实验 | 3 至 5 个 | 必须能观察中间结果，不能只有最终演示 |
| 失败案例 | 至少 2 个 | 说明失败原因、检测办法与缓解措施 |
| 练习题 | 8 至 15 道 | 包括解释、修改实验、设计和批判性思考 |
| 资料来源 | 论文 + 官方文档 + 本地实现 | 产品状态标注核对日期 |

## 叙事顺序

每章原则上遵循以下顺序：

1. 用具体任务、冲突或失败现象开场；
2. 给出最小定义，但暂不堆叠术语；
3. 通过反例划清边界；
4. 展开架构与数据流；
5. 用一个可以手算的小例子解释核心机制；
6. 进入代码实验，展示输入、中间状态和输出；
7. 对照 LangChain、LangGraph、Agent SDK、Claude Code 或 Codex 等真实实现；
8. 分析失败、成本、安全与生产取舍；
9. 总结本章证明了什么、没有证明什么；
10. 用练习题把读者带到下一章。

## 编排与版式

正文参考 `bojieli/ai-agent-book` 的阅读节奏，同时保持本书自己的案例和工程证据：

- 章标题保留“第 N 章”，正文二、三级标题不再重复 `1.1.1` 式编号；目录层级以 `##`、`###` 两级为主；
- 开头用具体产品或任务制造张力，紧接一段“阅读提示”和一段全章短答案；
- 三级标题承担完整问题，标题以下至少形成连续论述；更小的转折使用“**短句。**”作为段首，不继续增加四级标题；
- 关键定义、结论和边界用加粗短句，避免整段加粗；比较关系优先使用表格；
- 实验统一使用 `> **实验 N-M ★★：名称**` 引用块说明目标，再给出命令、关键输出、失败样本和结论边界；
- 需要第一次阅读跳过的实现优化放入 `> **进阶：...**` 引用块，不打断主线；
- 经验性、争议性和随时间变化的结论使用脚注就近引用，章末保留延伸阅读与独立资料台账；
- 全章尽量使用一个贯穿案例，把概念、公式、工具调用和最终验收连接起来；
- 练习标注难度，并提供验收标准或参考答案，避免只有问题没有反馈闭环。

## 框架与产品的写法

- 先讲原理和最小实现，后讲框架；
- 不把框架 API 列表当成正文；
- 不用单次 Demo 宣称方案可靠；
- Claude Code、Codex 等产品按 Model、Context、Tools、Runtime、Safety、Evaluation 六个维度拆解；
- 快速变化的模型名、价格、参数和功能只放在资料台账或带日期的专栏中；
- 产品博客里的经验数据不得直接外推为普遍结论。

## 图和实验的证据要求

图必须帮助读者回答一个问题，正文要解释读图顺序。实验至少记录：

- 环境和依赖版本；
- 输入、参数与随机种子；
- 关键中间结果；
- 成功或失败输出；
- 本实验支持的结论；
- 本实验不能支持的结论。

后续写作与审稿均以此文件为验收基线。
